# R2 实施任务：本地 admin、默认空间与员工开户

日期：2026-09-15。状态：R2 实现与合成验收已完成；见 [R2 验收记录](WORKSPACE_CENTRIC_R2_ACCEPTANCE.md)。

依据：[总体设计](../OVERALL_DESIGN_ZH.md)、[R1 接口证据](WORKSPACE_CENTRIC_R1.md)、[功能和权限表](WORKSPACE_CENTRIC_R1_MATRIX.md)。按下列顺序逐项实现、验证并继续，不跨入 R3–R6 的完整业务改造。

## 1. 固定实现边界

- 不修改 WeKnora v0.8.0 源码，不导入其 `internal/**`；使用原生 REST、配置和产品侧持久化。
- 单个独立本地 admin，安装者提供邮箱、用户名和密码密钥文件；不设通用默认密码。不支持普通员工本地密码注册。
- 本地 admin 初始是平台管理员和默认空间 Owner；系统管理员身份与原生四角色独立。
- 新员工只做一次默认空间 Viewer 开户；既有更高成员角色保持，移除后不自动加回。
- 业务接口继续拒绝无空间身份；只为安装、认证和开户设置受限通道，不整体放宽企业门禁。

主站 `/` 恢复已有会话：有有效空间直接进入，没有员工会话自动发起企业 OAuth；首次登录自动开户，失败进入状态/重试页。`/admin/login` 是独立本地管理员入口，过期返回该页；两种入口共享产品界面，后端核验真实身份。

## 2. R2-1：受控安装与 admin 账户

**输入：**空安装环境、受保护的 admin 身份/密码配置、私有上游地址；公司 OAuth 与模型配置沿用现有配置。

**实现：**新增产品安装命令，在员工入口未开放的安装窗口调用内部 `/auth/register`，使用 `tenantless`。通过 `WEKNORA_BOOTSTRAP_SYSTEM_ADMIN_EMAIL` 和受控 App 重启提升已存在账号；随后关闭公开密码注册，核对 `/auth/me` 的账号 ID 与 `is_system_admin`。不通过产品公开入口临时开放注册。

新增产品侧安装进度记录：固定安装记录、阶段、admin 用户 ID、默认空间 ID、成员凭证 ID/密钥引用、错误码和更新时间。敏感值不写入进度表、日志或报告。使用单安装锁串行执行；保留历史迁移，以新增迁移建立记录。

**输出：**持久化安装 admin ID，阶段为账户已准备；默认空间尚未建立时不能宣告员工入口就绪。

**失败恢复：**已有账号需验证为本次明确配置的安装账号，不接管同名陌生账号；已存在其他平台管理员时按原生规则停止自动提权，报告冲突。重启/重试只恢复未完成步骤，不重置密码或角色。

**验收：**空安装、重复运行、账号冲突、错误密码、提权前后重启、配置缺失、日志无密钥；新增迁移向前执行和回退/恢复验证。

## 3. R2-2：管理员产品登录与会话

**接口：**新增产品网关 `POST /api/v1/mindcreek/admin/auth/login`、`refresh`、`logout`、`change-password`，登录页 `/admin/login`。普通入口仍为企业 OAuth；本地页不提供注册。

登录请求复用原生 `email`/`password`；响应沿用原生登录 DTO 的 `token`、`refresh_token`、`active_tenant` 和 `memberships`。刷新复用原生 `refreshToken` 请求及 `access_token`/`refresh_token` 响应。改密沿用原生请求结构和密码校验，退出沿用原生令牌撤销。实现时以固定 v0.8.0 DTO 做契约测试，不将登录的 `token` 与刷新的 `access_token` 混淆。

每次登录/刷新取得原生凭证后，必须核对返回用户 ID 等于安装记录的本地 admin，且账号有效、仍是平台管理员，才返回凭证。拒绝不匹配主体并撤销此次产生的凭证。后续请求按该 ID 进入本地管理员认证分支，仍执行原生空间权限。员工令牌不能经此入口刷新或绕过企业停用状态。

**输出：**admin 从产品入口获得可用会话；普通员工保持企业认证。初始化未完成时 admin 只进入安装状态/恢复流程。

**失败恢复及验收：**OAuth 服务故障不影响本地 admin；也不开放员工密码登录。验证错误账号/密码、伪造前端角色、员工 refresh token、已撤销令牌、改密/退出后的失效、限流、无空间 admin 和恢复后的登录；新增可见登录页需前后截图。

## 4. R2-3：默认空间与成员自动化凭证

**输入：**账户已准备的安装记录和 admin 原生 bearer 会话。

**实现：**由安装流程调用原生 `POST /tenants` 创建默认空间，上游建立 Owner；保存固定空间 ID。随后以 Owner 创建只含 `manage_members` 的 API Key，令牌放入受保护密钥文件，记录 ID/引用。验证权限后将安装标记为就绪；凭证不进入浏览器。

上游创建空间不是幂等按名称接口。创建前记录阶段，成功后立即持久化 ID；请求结果不明时停止自动再建，提供显式“接管指定默认空间 ID”的恢复选项，核对该空间与安装 admin 的 Owner 关系。不得仅按名称匹配。安装已完成后的启动只检查状态，不再赋予 Owner；移交不会被启动流程撤销。

**输出：**固定默认空间 ID、初始 Owner 和可用成员自动化凭证，员工开户可以执行。

**验收：**重复/并发安装只执行一次创建；创建成功但落库前失败不盲目再建；指定 ID 恢复；凭证写入失败/撤销以及当前 Owner 显式更换凭证；所有权移交后重启不夺回；凭证无法管理其他空间或分配 Owner。

## 5. R2-4：员工首次开户

**输入：**已由现有 broker 验证的稳定企业身份、上游账户 ID/身份邮箱和就绪安装记录。

**接口：**`GET /api/v1/mindcreek/onboarding` 返回 `pending`、`joining`、`ready`、`failed` 或 `removed` 状态；`POST` 同一路径触发幂等开户/重试，不接收用户指定的空间 ID 或角色。返回状态、当前可用空间及非敏感错误码；默认成员角色由服务器固定为 Viewer。

**实现：**将有效新账户设为 `tenantless`，在企业身份表允许绑定本地用户 ID 而尚无本地空间；保留现有 `local_tenant_id` 非零或 NULL 约束。新增以稳定企业身份唯一关联的开户进度，记录本地用户、默认空间、尝试状态、完成时间和错误码。先验证企业账户有效，再允许该账户访问开户接口。

使用默认空间 `manage_members` 凭证直接加入。409 时读取已存在的活动成员关系，不覆盖已有 Contributor/Admin/Owner；只有核对成功才标为开户完成。刷新原生成员信息并选择可用空间。并发回调以用户级锁/唯一记录串行完成，网络失败保留可重试状态。

完成记录不随成员删除而清除；之后失去默认空间成员关系返回 `removed`，不重新加入。已有其他活动空间仍可按原生权限使用。没有可用空间时显示受限状态及退出，不建立个人空间。默认空间或服务凭证不可用时返回失败状态，不降级为广泛管理员调用。

**输出：**新员工的默认空间 Viewer 成员关系、当前空间和开户完成记录。

**验收：**合成 OAuth 首次/重复/并发回调；错误身份映射；进程重启；成员写入成功但进度保存失败；409 保留高角色；停用/恢复；移除后重复登录不加回；开户前 KB、Agent、搜索、文件和 MCP 均不可访问。

## 6. R2-5：创建空间与原生成员接口接通

**输入：**已认证用户、当前空间和原生四角色成员关系。

**实现：**产品 `POST /api/v1/tenants` 只接受平台管理员的真实人类 bearer 主体；本阶段拒绝机器 API Key 从产品入口创建空间。内部自建能力保持开启，但 `/auth/me` 等返回的创建能力按产品策略过滤；所有外部流量必须经过网关。核对 DB 系统设置优先级，初始化确定 `auth.default_tenant_mode=tenantless` 等开户配置，并阻止产品设置入口将其改成与企业开户策略冲突的值。

恢复适用于已登录员工的原生成员、邀请、邀请接受和角色修改路由；继续关闭普通密码注册与依赖密码建号的邀请注册。人类成员操作使用操作者的原生 bearer，不能统一改为服务密钥。空间创建者初始为 Owner；空间 Admin 不获得成员变更权限。

成员/邀请输入使用企业邮箱时，通过已有企业身份映射取得上游身份邮箱；未开户用户明确返回尚未建号，R2 不预造员工账户。保留原生四角色响应、最后 Owner 约束和目标空间检查。所有权移交按“接收者成为 Owner → 原 Owner 降级”两步恢复，不改变平台身份。

**输出：**仅平台管理员可创建空间；原生 Owner 可管理当前空间成员；邀请员工经企业登录接受。

**验收：**普通 Viewer/Contributor/Owner 及 API Key 不能从产品入口建空间；platform admin 创建后为 Owner；跨空间篡改拒绝；Owner 邀请及接受；Admin/Contributor/Viewer 成员写入拒绝；四角色升降级、最后 Owner、两步移交中断重试及平台身份不转移。

## 7. R2 完成条件与后续边界

- 上述五项分别提交对应实现、测试和文档；新增迁移具有升级/恢复验证。默认空间、admin 与开户记录中的非敏感标识可审计。
- 回归现有 OAuth 和托管模型；运行受影响的网关、路由清单、部署配置和前端检查。可见改动提供截图，缺失的真实企业登录/目标环境证据明确留给后续验收。
- R2 不停用旧知识授权链，不恢复整套 KB UI，不实现四工具 MCP、批量部门同步或网页小助手；这些分别按 R3–R5 执行。
- R1 已验证的是公开 API 的可行性；持久化幂等开户、admin 产品入口和跨服务恢复必须由 R2 的新实现与测试证明，不能直接引用 R1 探针作为完成证据。
