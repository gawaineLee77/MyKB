# MindCreek 以空间为中心的改版方案

日期：2026-09-22。状态：R1 设计与合成接口验证已交付；R2 实现与合成验收见 [R2 记录](WORKSPACE_CENTRIC_R2_ACCEPTANCE.md)；R3 后端已实现，见 [R3 验收](WORKSPACE_CENTRIC_R3_ACCEPTANCE.md)；R4 页面实现与合成验收已完成；R5 实现与合成验收已完成，见 [R5 记录](WORKSPACE_CENTRIC_R5_ACCEPTANCE.md)；R6 企业环境待验。

本方案记录新的产品方向及实施顺序；权威要求见[总体设计](../OVERALL_DESIGN_ZH.md)，结果见[R1 验收记录](WORKSPACE_CENTRIC_R1.md)。用户已确认尚未部署使用，采用独立本地 admin，普通员工使用企业 OAuth2；历史 Phase 0–5 记录保留供追溯。

## 1. 结论与新范围

不回退到 Phase 0，不降级 WeKnora，不回滚数据库。以当前批准的 WeKnora v0.8.0 和 Phase 5 的模型、身份、部署能力为基础，移除旧产品模块，改造空间授权和员工入口。

新目标：

- 取消 MindCreek 的知识库发布、目录、订阅和 Personal Notes 产品功能。
- Owner、Admin、Contributor 按原生权限使用 WeKnora 知识库和智能体页面，沿用其处理与问答引擎。
- 新员工首次企业登录只建立账户，并以 Viewer 加入公司默认空间，不创建个人空间。
- 独立本地 admin 账户初始化为平台管理员和默认空间 Owner；密码由安装密钥配置提供，用户名本身不授予权限。
- 默认 Viewer 员工使用对话工作台，可选择获授权的空间、智能体和知识库，并阅读回答引用；被授予 Contributor 或更高角色后显示对应原生功能入口。
- 平台管理员可以创建空间、指定初始所有者；空间 Owner 可以添加成员、修改角色、移交所有权。
- 保留原生 Owner、Admin、Contributor、Viewer 四种角色及其管理功能。Owner/Admin 管理空间资源，Contributor 创建并管理自己的知识库和智能体，具体操作遵循上游角色、资源归属和共享权限检查。
- 智能体可作为其他网页中的小助手；保留现有默认模型和企业 OAuth2 登录。

网页小助手已由用户确认为“仅企业登录员工使用”，沿用员工空间权限。匿名访问不在本次范围。

## 2. 权限与页面

### 平台权限和空间角色

平台管理员与空间角色分开。admin 初始同时拥有两者；普通 Owner 不因管理一个空间而获得创建其他空间或修改全局模型的权限。公司默认空间、首次加入角色、仅平台管理员创建空间属于本次企业开户与部署策略，不重新定义原生四种空间角色、权限等级或成员管理规则。

| 操作 | 平台管理员 | 空间 Owner | 空间 Admin | 空间 Contributor | 空间 Viewer |
|---|---|---|---|---|---|
| 创建新空间（企业部署策略） | 是 | 否 | 否 | 否 | 否 |
| 添加成员、修改成员角色 | 在自己拥有的空间中 | 是 | 沿用当前上游 Owner 限制 | 否 | 否 |
| 移交空间所有权 | 在自己拥有的空间中 | 是 | 否 | 否 | 否 |
| 创建知识库、智能体 | 依据目标空间角色 | 是 | 是 | 是 | 否 |
| 修改已有知识库、智能体 | 依据目标空间有效权限 | 原生权限 | 原生权限 | 原生归属/共享权限 | 原生归属/共享权限 |
| 问答、知识检索、查看引用 | 依据目标空间成员关系 | 是 | 是 | 是 | 是 |
| 全局默认模型、身份配置 | 是 | 否 | 否 | 否 | 否 |

保留四种角色的原生展示、邀请时分配、角色修改和成员管理入口。新员工默认加入为 Viewer；Owner 可按原生流程调整为 Contributor、Admin 或 Owner。既有 Contributor 保持原角色，不因本次改版批量降级或升级。

完整沿用上游 RBAC、资源归属及共享权限语义，不增加统一 Admin 写入门槛。Contributor 可以创建并管理自己的资源；对他人资源依照原生有效权限执行。部分原生写接口存在“创建者或 Admin”规则，角色变更后的结果仍以上游实际授权为准，不新增“Viewer 一律不能修改其曾创建资源”的产品规则。

Viewer 默认导航保留对话、历史、必要的账户操作以及对话内的空间/智能体/知识库选择器，隐藏管理入口。Contributor 显示知识库和智能体入口，Owner/Admin 显示各自获准的管理入口；切换空间或变更角色后同步更新。页面与操作检查沿用原生有效权限，导航收敛不改写资源归属授权。引用预览仍可用；“只见对话页”不意味着回答所需的知识检索与引用接口全部关闭。

### 知识访问规则

新建空间中的知识按空间成员授权；员工能使用其所属空间中面向 Viewer 开放的智能体和知识库。不再经过个人 KB Owner、产品分享 grant、发布和订阅的旧授权链。

保持上游原生资源与共享语义；跨空间共享能力需单列兼容测试，不把本次改版扩展为自动创建跨空间共享关系。员工会话仍按用户隔离，成员移除、停用、角色降级在后续请求重新鉴权。

## 3. 模块处理

| 现有模块 | 改动 |
|---|---|
| WeKnora 子模块、文档解析、存储、索引、检索、Agent 引擎 | 保留当前批准版本，不重建引擎 |
| `identity`、OAuth2/OIDC broker、企业身份绑定、停用/恢复、注销 | 保留，补充无空间账户的受限开户流程和默认空间加入 |
| `managedmodel`、声明式内置模型、密钥注入、连通性检查 | 保留；原生创建知识库和配置 Agent 的调用重新接入默认模型策略 |
| 网关、路由清单、审计、观测、TLS、镜像、备份恢复 | 保留；按新接口与权限矩阵修订 |
| `publication`、`catalog`、`subscription`、发布/订阅 UI/API | 从新运行组合中移除；历史数据保留待处理 |
| `note`、`notespolicy`、笔记配额/修订 UI/API | 停用产品入口；不自动删除或公开原笔记 |
| 产品 `KnowledgeLibrary`、`CreateKnowledgeSpace`、`RAGWorkspace`、`NotesWorkspace` | 恢复原生知识库列表、创建、详情、上传和设置页面 |
| 旧 KB `authorization`、`grant`、`library`、`agentscope` | 解除个人授权/订阅依赖，以当前成员关系和上游资源授权替换，保留必要的范围检查 |
| `profile`、`preset`、`ingestion` | 移除强制 Personal Notes / Plain RAG 产品模式的依赖，保留仍适用的模型与上传策略 |
| MCP | 本次需求未取消；保留只读能力，移除 `list_publications`、`list_subscriptions`，其余工具迁移到空间授权 |
| 现有社区导入工具 | 保留工具与归档；上传/创建接口适配原生知识库并回归 |

原生知识库一致性以批准的 v0.8.0 为基准，包括文档/FAQ、上传、处理、配置和检索工作流。不得继续把全部知识库强制设为旧 Plain RAG 预设。原生 Wiki/图谱等选项需核对模型、索引、异步任务及部署依赖后列入支持矩阵；不因此引入自研 PixelRAG、本体或其他未要求的扩展。

前端覆盖脚本按用途拆分：品牌、企业登录、默认模型、角色导航、小助手适配。取消知识库页面替换，保留仍必要的模型和身份补丁；管理页面与原生页面的差异有明确清单。

## 4. 默认空间与成员管理

### 初始化

在员工业务入口开放前，通过内部注册和上游初始化建立指定本地 admin，关闭公开密码注册，为其建立平台管理员权限，创建或绑定公司默认空间，并确认 Owner 成员关系。日常 admin 登录、刷新、改密和退出经过产品网关；普通员工继续使用企业 OAuth2，不复用应急旁路作为日常入口。不能把首位普通登录员工自动升级为 admin，也不能在每次重启时把已移交的空间抢回原 admin。

以服务端固定的默认空间 ID 识别空间，不按可重名/可修改的名称匹配。创建和成员写入必须支持重复执行与失败恢复。

### 新员工首次登录

1. 保留现有企业 OAuth2 验证和稳定企业身份映射。
2. 将上游新用户空间策略设为 `tenantless`，创建本地账户。
3. 由产品开户服务以受限的成员管理权限加入默认空间，角色固定 Viewer。
4. 刷新当前空间与成员信息，进入对话工作台。
5. 在成员关系完成前，仅允许身份、开户状态、重试和退出等必要接口，禁止进入知识操作。

当前 `identity.Gate` 要求 principal 已有非零空间，不能只修改环境变量：必须增加受限的无空间开户通道，避免首次登录陷入拒绝循环。与上游的多次 REST 调用采用持久化进度和幂等恢复，不假设跨服务事务天然原子。

自动加入只针对新账户开户，或明确的既有用户迁移批次。Owner 后续移除用户后，不应在下一次登录静默重新添加。部门同步不属于本次必需交付，可在成员开户服务上另行扩展。

### 仅 admin 创建空间

现有全局“关闭自建空间”只对跨空间特权主体等保留例外，普通系统管理员没有独立豁免。优先验证以下不改上游方案：

- 产品网关将 `POST /tenants` 限制为指定的平台管理员，并过滤 `/auth/me` 的创建能力；浏览器只展示匹配的入口。
- 上游自建开关作为内部执行依赖开启，使用当前已认证管理员的请求创建，上游自动赋予该管理员 Owner。
- 上游 App 保持私有，所有外部访问经过网关，不能通过另一个端口或入口绕过产品限制。

这避免仅为创建空间而授予 admin 跨空间内容访问权。实施前验证无空间管理员的初始化、所有创建入口及 API Key 路径；如公开 REST 无法满足某个不变量，再按上游补丁台账准备最小提案。

### 添加成员与所有权移交

保留上游原生成员列表、邀请、四种角色分配/修改、移除及所有者约束的界面和接口。默认空间开户使用直接加入接口；批量导入如实施，可作为现有 API 的批量调用，未开户员工保存待关联记录，不替换原生成员管理流程。

所有权移交复用原生角色关系：先确保接收人已成为 Owner，成功后再将原所有者降级。全过程不能出现零 Owner；记录操作者、前后角色，重复提交可恢复。平台管理员权限不会随某个空间的所有权移交自动转移。

## 5. 网页小助手

WeKnora 已有 Embed Channel、Widget 和 iframe 页面，可复用其界面、渠道配置及聊天组件。当前 MindCreek 明确禁用了 embed 路由和设置入口，需要有选择地接回。

原生安全模式通过后端用长期发布令牌换取约 30 分钟的短时渠道令牌。当前代码把短时令牌绑定到渠道，EmbedAuth 注入的是渠道虚拟用户；它不天然绑定企业员工，也不会逐次检查员工的空间成员关系。

企业员工模式的目标：

- 在原生 Agent 管理界面提供网页发布/嵌入入口，配置智能体、来源域名、启停和限流。
- 宿主网页仅承载小助手；企业 OAuth2 登录在顶层页面或受控弹窗完成，登录后返回已验证的入口。
- 网关对每次聊天、历史、上传及引用请求验证真实员工、当前空间成员关系、渠道状态和会话归属。
- 优先验证 Widget/Embed 聊天组件对产品会话接口的适配；也可由网关维护员工与原生渠道会话的绑定。仅在签发渠道令牌时检查一次登录不足以满足成员撤销要求。
- 不向浏览器下发长期发布令牌、共享 API Key、OAuth 客户端密钥或模型密钥；不以发布者的账户身份替员工问答。
- 以独立宿主网页验收 iframe、Cookie 限制、CSP、Origin、SSE、图片和引用，以及两个员工的会话隔离和撤销。

智能体网页发布单独保留，与本次取消的“知识库发布/订阅”使用不同模块和术语。现有渠道设计中的 KB 组织公开、订阅前提需要删除，不照搬旧 AP 全量计划。

## 6. 首次安装与数据边界

用户确认尚未部署使用，本次以首次安装和备份恢复为交付主线，不安排现网用户数据迁移，也不清理现有本地开发数据。以下规则仅用于后续另行纳入的已有数据环境升级，当前不执行：旧私有 KB、笔记直接落入多人空间会扩大可见范围，必须先盘点。

- 先盘点账户、个人空间、成员角色、KB/Agent 归属、笔记、分享、发布、订阅、会话和引用。
- 公司默认空间优先新建或选择已确认用途的空间；不直接把某位用户旧个人空间设为公司默认空间。
- 旧知识库按明确清单迁入团队空间；未列入清单的内容留在隔离的旧空间/归档中。停止笔记功能不等于删除笔记数据或转为全员可读。
- 不自动把已订阅用户变成源空间成员；那会授予源空间中其他知识的访问权。
- 保留已有四种空间角色及原生资源归属；空间迁移中的成员关系映射单独列清单，不批量重映射 Contributor，也不按最高权限统一提升。
- 保留现有模型 ID、Embedding 维度和索引配置；本次改版不要求全量重建索引。跨空间迁移涉及存储、索引、关联资源，必须验证上游支持的迁移/复制流程，不能只改 `tenant_id`。
- 原迁移文件不改写、不执行旧 Phase 的整套 down；旧业务表先保留，新版本停止依赖。回退验证覆盖旧数据恢复和新版本写入，不能仅回滚前端镜像。

## 7. 实施顺序与验收

建议以 R1–R6 作为本次改版的独立编号，保留历史 Phase 0–5 记录。先完成企业内部使用闭环，再接网页小助手，最后完成首次安装、恢复和生产落地。R1 已完成设计与合成验证；R2 已完成实现与合成验收，R3 后端完成合成验收；R4 页面实现与合成验收已完成，R5 实现与合成验收见 [R5 记录](WORKSPACE_CENTRIC_R5_ACCEPTANCE.md)，R6 待企业目标环境验收。

| 阶段 | 交付物 | 关键验收 |
|---|---|---|
| R1：设计基线与接口验证 | 更新设计和路线图，明确原生功能范围，验证开户/建空间/嵌入接口 | 新旧范围可追溯；关键接口有可行路径，未解决的限制有明确记录 |
| R2：默认空间与员工开户 | admin 初始化、无个人空间建号、自动加入 Viewer、平台创建空间、原生成员 API | 重复执行可恢复；普通用户不能建空间；移除成员不被自动加回 |
| R3：空间授权与服务改造 | 原生四角色和资源授权接管，保留模型/OAuth，退役旧业务依赖，更新 MCP | Contributor 权限保留；检索前鉴权；停用/移除、跨空间、会话与引用隔离 |
| R4：原生页面与内部使用闭环 | 原生 KB/Agent/成员页面、Viewer 对话工作台、批量成员导入、所有权移交 | 四角色菜单与操作正确；无需个人模型密钥；管理、问答及成员流程完整 |
| R5：企业网页小助手 | Agent 网页发布配置、员工登录、独立宿主网页嵌入 | 每次请求保留员工身份；渠道/员工撤销生效；跨用户会话和引用隔离 |
| R6：首次安装、试点与发布 | 全新安装、备份恢复、镜像和手册、目标环境试点 | admin/默认空间初始化可恢复；真实身份与模型验证通过；无现网迁移任务 |

### R1：建立设计基线，提前验证关键接口

**目标：**明确这次交付替代哪些旧能力，并提前解决可能影响实现路线的接口限制。

- 同步 `OVERALL_DESIGN.md` 及中文版、`CURRENT_STATUS.md`、`ROADMAP.md`，区分新目标、当前实现和历史完成记录。旧笔记、发布/订阅相关未完成事项标为取消或被取代，不标为已实现。
- 保存可复现的当前工作树、上游版本、配置结构及基线检查结果；已有未提交工作也要纳入记录，不能只记 Git HEAD。先盘点数据规模和归属，不进行迁移或删除。
- 建立 v0.8.0 原生知识库/智能体功能对照表、四角色权限与路由表、保留/退役模块清单。Wiki、图谱等原生能力逐项列出部署依赖和验证方式；额外自研 GraphRAG、PixelRAG、本体路线不混入本次改版。
- 用最小接口验证确认：`tenantless` 员工开户、指定 admin 初始化、仅平台管理员创建空间、原生成员加入与角色变更。
- 提前验证企业小助手的登录与会话适配路线，包括独立域名下的 OAuth 往返和真实员工身份传递；完整产品放到 R5。

**完成条件：**关键接口验证结果和剩余限制可审查；明确哪些能力由配置、网关、REST 适配或前端覆盖实现。如确实需要上游补丁，仅对受影响部分执行补丁台账规定的提案与评审，其余工作继续。

### R2：完成默认空间和员工生命周期

**目标：**从新安装开始，得到稳定的 admin、默认空间和员工成员关系。

- 实现幂等初始化：识别指定 admin，创建或绑定默认空间，建立初始 Owner，服务端记录固定空间 ID；重启不撤销后来进行的所有权移交。
- 保留企业 OAuth2/OIDC，增加受限开户流程：无个人空间建号 → 默认空间 Viewer → 刷新当前空间 → 可进入业务。开户未完成时只开放必要的恢复接口。
- 实现平台管理员创建空间，复用原生添加/邀请、角色修改和移除接口；空间角色不赋予平台权限。
- 区分“首次开户加入”与“每次登录同步”：成员被移除后不自动加回；默认空间不可用时返回可恢复状态，不临时创建个人空间。

**完成条件：**并发首次登录、重复回调、成员写入失败重试、停用/恢复、所有者变更后重启均通过；不会产生额外个人空间或自动提权；客户端伪造角色和绕过网关创建空间被拒绝。

### R3：让原生空间授权接管业务接口

实现与接口证据见 [R3 验收](WORKSPACE_CENTRIC_R3_ACCEPTANCE.md)。原生后端使用独立运行组合，旧界面恢复清单见 [R4](WORKSPACE_CENTRIC_R4.md)。

**目标：**知识库、Agent、检索、会话、引用和 MCP 使用一致的有效权限，解除旧个人知识产品的依赖。

- 在隔离的新环境和新空间中接通原生接口。传递真实用户与当前空间，保留上游四角色、创建者及共享权限检查；产品负责企业身份状态、开户和既有必要范围约束，不另建角色体系。
- 原生创建 KB、Agent 及运行请求接入已有托管模型策略，保留默认 Chat、Embedding、Rerank 和可选 VLM；普通用户无需填写密钥，已有模型 ID 与索引配置保持可用。
- 逐条迁移旧 `authorization`、`grant`、`library`、`agentscope` 依赖；新路径接管后，再从新运行组合中移除 publication/catalog/subscription/note 及旧预设依赖。退役接口返回明确的不可用结果，不能落入宽泛代理路由。
- MCP 保留仍适用的四个只读工具，删除发布/订阅工具，并用相同空间权限验证工具发现、搜索和内容读取。社区导入工具同步适配原生创建/上传接口。
- 旧空间数据在完成可见性盘点前保持隔离，不直接接入新的空间可见规则。跨空间共享、Agent 绑定知识范围、API Key 和流式接口都纳入路由核对。

**完成条件：**用两个空间和四种角色验证原生允许/拒绝行为，包含 Contributor 管理自有资源、角色变化后的原生归属规则、非成员访问、账户停用、成员撤销、会话/文件/引用隔离。授权在检索前执行，不能靠隐藏菜单补足后端检查。

### R4：交付企业内部可完整使用的版本

实施和本轮证据见 [R4 验收](WORKSPACE_CENTRIC_R4_ACCEPTANCE.md)，运行说明见 [R4 配置](../../deploy/r4/README.md)。

**目标：**管理员配置内容，员工登录后即可问答；成员管理无需等待网页小助手完成。

- 恢复原生知识库列表、创建、详情、文档/FAQ、处理状态和设置页面，以及 Agent 和成员管理页面。按 R1 对照表验证原生功能，拆分并保留品牌、OAuth、托管模型等必要覆盖。
- Viewer 使用对话、历史和对话内的空间/Agent/知识库选择器；Contributor、Admin、Owner 在当前空间显示原生允许的入口。切换空间、刷新或成员角色变化后重新计算菜单；深链接处理与导航一致，资源授权仍遵循原生规则。
- 保留原生四角色分配、邀请、移除和最后 Owner 约束。完成所有权移交流程；明确移交空间不等于转移平台管理员身份。
- 提供按邮箱列表或 CSV 批量加入已有账户的工具/入口，支持预览、逐行结果、重复处理和失败重试。复用原生成员 API，不改变既有角色；对未开户账户明确报告未加入，或保存经审核的待关联记录。
- 移除发布、订阅、目录和个人笔记菜单、页面、按钮及旧链接入口；引用预览和必要的账户/退出操作仍可用。

**完成条件：**完整演示 admin 建空间及管理成员 → Owner/Admin/Contributor 按各自权限管理 KB/Agent → 新员工以 Viewer 登录并问答 → 移除员工后失去对应访问。四角色和切换空间的截图、前端测试/类型检查/构建均有结果，默认模型与 OAuth 回归通过。

R4 是首个内部功能里程碑。可使用合成数据进行演示和联调；进入真实员工试点前仍需完成 R6 中适用于该发布范围的数据、恢复和目标环境检查。

### R5：发布仅供企业员工使用的网页小助手

**目标：**员工在另一个网页使用已发布 Agent，访问范围与主站一致。

- 在原生权限允许的 Agent 管理入口接入网页渠道配置：来源域名、启停、限流和嵌入代码。渠道发布权限也按原生能力核对，不因为 Contributor 可以编辑 Agent 就自动提升其渠道管理权限。
- 落实 R1 验证过的企业登录和会话适配；服务端绑定员工、渠道、空间和会话，每次聊天、历史、上传及引用请求重新校验。
- 用独立宿主网页完成顶层/弹窗登录、Cookie/CSP/Origin、SSE、图片和引用流程。验证两名员工的会话隔离，以及退出、账户停用、成员移除和渠道关闭。

**完成条件：**浏览器没有长期发布令牌或共享密钥；员工不能利用渠道身份获取额外权限，历史会话和引用不能绕过撤销。主站功能完整性不依赖该渠道开启。

### R6：首次安装、受控试点和发布交付

**目标：**将新产品首次部署到企业环境，并验证恢复和运行质量。

- 验证空环境初始化、本地 admin 登录、默认空间和首位员工 Viewer；验证重启、重试、失败恢复及新版本写入后的备份恢复。
- 保留历史迁移文件和本地开发数据；不执行现网迁移或退役表/存储的物理清理。若以后需要已有数据升级，按第 6 节另列映射和迁移验收。
- 交付版本化镜像、配置模板、首次安装/恢复手册及验收报告，记录产品工作树、上游 commit 和镜像的对应关系。
- 在目标环境验证真实 OAuth、模型、证书/代理、上传解析和问答质量、告警及资源使用；先小范围员工试点，再按发布授权扩大使用。

**完成条件：**首次安装与恢复证据齐备，真实身份、模型和适用网页渠道验证通过。代码交付、目标环境验收和生产发布分别记录。

### 交付节奏与可后置事项

- **内部主站里程碑：R1–R4。** 覆盖默认空间、四角色、成员管理、原生 KB/Agent、访客问答、模型和 OAuth。
- **网页小助手里程碑：R5。** 接在同一身份和空间权限基础上，避免形成第二套用户体系。
- **生产落地里程碑：R6。** 如先上线主站，可以先执行不含小助手的 R6 验收，保持渠道关闭；小助手完成后再补该渠道的发布验收。
- **部门能力可后续增量交付。** 第一层是管理员筛选部门后一次性批量加入，建立在 R4 批量成员能力上；需要可信部门标识或目录来源。第二层才是持续同步，另行确定转岗、离职、手工角色覆盖及冲突规则。一次性导入不承诺后续自动同步。
- 自研 PixelRAG、本体、桌面版、企业小程序等独立路线暂不与本次改版并行推进；原生知识库功能仍按 R1 对照表交付。

以纵向小步骤实现，不允许出现“旧授权已拆除，新授权尚未接管”的可部署中间态。可以在独立新运行组合中完成适配后整体切换；避免长期维护两套并行授权规则。

每阶段交付对应代码/配置、测试证据、文档和未完成事项，按依赖顺序继续已授权范围，不把进度汇报作为逐项确认点。涉及上游例外补丁、实际数据迁移或生产发布时，遵循其适用的授权与评审边界。

复用仍有效的上游边界、OAuth、模型、备份和迁移测试；删除功能的断言转为接口不可用和兼容/迁移检查。维护 `phase0-check`、`phase1-gateway-test`、`stage1-check`、`product-test-frontend` 等检查的有效部分，同步调整旧 Phase 5 的功能断言，并建立本次改版的验收入口。不把旧 Phase 5 全绿视为新需求验收；未获得截图、真实 OAuth 或目标环境证据的项目如实记录为待验证。
