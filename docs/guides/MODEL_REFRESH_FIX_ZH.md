# 问答与智能体误报“模型未配置”的修复

本次合并修复版本为 `current-20261020-699031ce-104658`，Linux AMD64 完整离线包，包含模型缓存修复和历史图片权限修复。验证范围及环境限制见[本次验收记录](../plans/CURRENT_AMD64_MODEL_FIX_20261020.md)。此前的 `current-20261020-699031ce` 图片修复包不包含本次模型缓存修复；无需先安装该包，可以从 R4 图谱版、1009 或 1019 直接升级到合并修复包。

2026-10-21 的知识库列表后续修复目前仅完成源码和本地验证，尚未构建升级包；上述已封存版本不包含此修复，详见[后续修复记录](#2026-10-21-知识库列表后续修复未封包)。

## 原因与临时处理

页面首次打开时模型正常，切换窗口或标签页后显示“未配置”，智能体出现橙色感叹号；重新选择原模型又恢复。这一现象已在旧版实际编译页面中复现。

旧逻辑在窗口重新获得焦点、标签重新可见或知识库权限变化时，清空所有资源缓存，却只重新加载知识库。模型和智能体的本地列表因此变空，界面将其误判为配置缺失。这里没有“模型配置过期”的定时器，也没有向后台发送删除或修改模型的请求。

升级前可以暂时重新选择原模型，或重新加载整个页面。该缺陷无需通过修改 `enterprise.env`、重填模型密钥、删除智能体或重启服务解决。若重新加载后仍异常，应另查模型列表接口和模型服务；不能把所有模型故障都归因于此缺陷。

## 修复后的行为

- 同一账号、空间及角色返回页面时，保留已经成功读取的模型列表，并重新获取模型、智能体和知识库。
- 模型列表请求短暂失败时保留已有列表；后台成功返回空列表时，仍如实显示模型未配置。
- 知识库和智能体的可访问列表重新核验，已撤销的知识库从选择中移除。
- 刷新前发出的旧知识库请求不能在撤权后重新写回缓存，也不能清除后续请求的状态。
- 账号、空间或角色变化仍清空全部资源并重新进入页面。

合并包同时保留历史图片权限修复及 `bin/image-resources` 检查／人工确认工具。图片自动恢复的条件与限制见[历史图片恢复说明](IMAGE_PERMISSION_RECOVERY_ZH.md)。

## 升级

保留原包与实例目录，将合并包解压到新目录。先在压缩包所在目录校验相邻 `.sha256` 文件，再进入新包目录：

```sh
sha256sum -c mindcreek-current-20261020-699031ce-104658-amd64.tar.gz.sha256
```

以下环境变量必须使用正在运行的原实例值：

```sh
export MINDCREEK_STATE_DIR=/EXISTING_INSTANCE_DIRECTORY
export MINDCREEK_PROJECT=existing-compose-project

python3 bin/mindcreek verify
python3 bin/mindcreek load
python3 bin/release plan --from-package /OLD_FULL_PACKAGE_DIRECTORY
```

核对计划，在维护窗口暂停业务写入，使用尚不存在的备份目录执行：

```sh
python3 bin/release upgrade \
  --from-package /OLD_FULL_PACKAGE_DIRECTORY \
  --backup /SAFE_BACKUP_DIRECTORY/before-model-and-image-fix

python3 bin/mindcreek ps
python3 bin/mindcreek install status
```

不要执行 `init` 或删除数据卷。升级停止容器后，冷备份较大的数据卷可能需要较长时间；不要并行启动第二次升级。回退使用原包及整套升级前冷备份，遵循[企业升级说明](ENTERPRISE_DEPLOYMENT_AND_UPGRADE_ZH.md)。

## 升级后验证

保持外部流量暂停，完成验收后再恢复访问。R4／1009 首次迁入新的权限体系时，还需按[企业升级说明](ENTERPRISE_DEPLOYMENT_AND_UPGRADE_ZH.md)核对历史知识库可见性和旧 API Key 范围；服务启动成功不代表这项访问权限复核已经完成。

重新加载浏览器页面以载入新前端资源，然后：

1. 打开问答页面，确认原模型名称与智能体配置正常。
2. 切换到其他窗口或标签页，再切回，重复几次；不重新选择模型，检查名称和智能体状态仍正常。
3. 发送一条实际问题，确认模型能够回答。页面列表正常不等于已验证模型供应方连通性。
4. 检查同一张历史图片在知识库文档和问答中的显示。
5. 对测试成员撤销一个知识库的可见权限，再切回该成员页面，确认知识库及图片不再可用。

本地浏览器验收使用合成数据；真实企业登录、模型服务及目标 Linux AMD64 数据库检索仍需在实际部署环境验收。

## 2026-10-21 知识库列表后续修复（未封包）

已复现窗口返回后知识库列表突然显示“暂无知识库／创建第一个知识库”，但刷新或重新进入页面恢复的缺陷。列表页与全局空间刷新各自发起请求，较早请求失效后返回的空结果覆盖了页面；同时，权限检查仍在进行或接口暂时失败，也被当成没有可见知识库。

此问题来自共用刷新逻辑，可能影响 Owner、Admin 和 Contributor 的知识库页面。Viewer 没有知识库管理入口，本轮单独验证了其问答中的可见知识库选择和撤权处理。

本轮在产品前端覆盖层完成以下修改，未修改上游源码、权限规则或数据库：

- 窗口返回、标签可见和权限变化由同一个刷新协调器处理，刷新期间收到的事件会安排后续核验。
- 列表和权限作为同一批结果提交；账号、空间、角色或筛选范围变化后，旧请求不能覆盖当前页面。
- 查询和权限核验期间显示加载状态；暂时失败显示错误和“重试”，不展示创建第一个知识库的空态提示。
- 后台确认无可见知识库时正常显示空态；真实撤权仍移除知识库及问答选择，不保留未经重新确认的访问权限。
